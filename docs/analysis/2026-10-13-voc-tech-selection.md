## 决策 1：主题建模框架 —— 为什么用 BERTopic 而不是手写管道

### 候选 A：BERTopic（选定）
一站式主题建模框架：`嵌入 → UMAP 降维 → HDBSCAN 聚类 → c-TF-IDF 主题表示 → LLM 命名`，模块化可插拔。

**依据**：
- 嵌入→聚类→表示的管道已被调好，不用自己拼（官方文档 [1]：HDBSCAN 是其默认且推荐的聚类器，专为短文本场景优化）
- **内置 LLM 主题命名钩子**：`OpenAI` representation 类 + `.generate_topic_labels()`，正好接我的簇命名三阶段——省掉自己写"簇内样本→prompt→命名"的管道 [4]
- c-TF-IDF 自动提取每簇关键词，可作为 LLM 命名的输入特征（比裸文本喂 LLM 更省 token、更聚焦）
- 支持 `set_topic_labels()` 手动/自动改标签 [4]，命名复查有落点

**代价**：引入一个框架级依赖，学习其 API；但比手写管道 + 自己调 UMAP/HDBSCAN 参数的总成本低。

### 候选 B：手写 sentence-transformers + HDBSCAN
完全可控，但要自己处理：UMAP 降维参数、HDBSCAN 的 min_cluster_size 调优、c-TF-IDF 主题表示、命名管道——每一步都是调参坑，且 BERTopic 已经把这些调好了。

### 权衡与决策
**选 BERTopic**。理由：VoC 的核心难点是**簇命名质量**（用户 Q5 决策），不是聚类管道本身。把管道交给成熟框架，把精力放在命名三阶段复查上——这才是本项目的差异化价值。手写管道是把时间花在被解决的问题上。

## 决策 2：嵌入模型 —— 中文效果与成本

### 候选 A：BGE-M3（首选）
智源 BAAI 的多语言嵌入模型，100+ 语言，支持 8192 token 长文本，dense+sparse+multi-vector 一体 [4]。

**优势**：BAAI 专门优化中文检索/聚类任务，中文语义空间质量业内公认强于通用多语言模型；开源本地跑，零边际成本。

**代价**：模型较大（~2GB），首次下载慢；推理比 MiniLM 慢（但评价量级几千条，可接受）。

### 候选 B：paraphrase-multilingual-MiniLM-L12-v2（兜底）
sentence-transformers 官方多语言模型，50+ 语言，384 维，轻量（~500MB），明确标注"可用于聚类和语义搜索" [2]。

**优势**：轻、快、成熟。**劣势**：中文语义质量弱于 BGE 系列（通用多语言模型对中文的优化不如 BAAI 专门模型）。

### 候选 C：LLM provider embedding（Ark/OpenAI text-embedding）
按 token 计费。几千条评价一次嵌入成本可忽略，但**反复调参重跑**时成本累积；且引入网络依赖。

### 权衡与决策
**首选 BGE-M3，MiniLM 兜底**。理由：中文效果是簇质量的上游——嵌入差了，聚类和命名再好也救不回。BGE-M3 的中文优化是最强的已知信号。[需 spike 验证]：用同一批小样评价，分别跑 BGE-M3 和 MiniLM，看簇内聚度（同类卖点是否聚在一起）——这是唯一可靠的选型验证，公开基准没有手游外设评价的直接数据。

## 决策 3：聚类算法 —— HDBSCAN，且为什么 KMeans 不合适

### HDBSCAN（选定）
- **簇数自适应**：卖点数量未知，不需要预设 k
- **噪声识别**：标记离群点为 -1，不强行归簇——电商评价噪声大（广告、无关内容、一句话好评），强行归簇会污染卖点簇
- 短文本小数据集适配好 [3]：密度聚类对"稀疏高维 + 样本量不大"友好

### KMeans（排除）
- 必须预设 k——卖点数量恰恰是要发现的东西，预设 k 本末倒置
- 强行划分所有点（无噪声概念），无关评价被塞进卖点簇，污染命名输入
- 文档明确指出：小数据集上 KMeans 因为是"划分而非真聚类"表现差 [1]

### 决策
**HDBSCAN**（BERTopic 默认，不用额外决策）。关键参数 `min_cluster_size`：[需 spike 验证]，小样数据从 5-10 起步调——太小产生碎簇，太大漏掉小众卖点。

## 决策 4：中文分词 —— c-TF-IDF 的必需适配

BERTopic 的 c-TF-IDF 默认用 CountVectorizer（英文空格分词）。中文没有空格，**必须接 jieba 分词**，否则 c-TF-IDF 提取的"关键词"是整句，主题表示失效。

**方案**：自定义 CountVectorizer，tokenizer 用 `jieba.lcut`，加载中文停用词表。这是 BERTopic 中文适配的标准做法，无备选（不jieba就废掉 c-TF-IDF 这一路）。

## 决策 5：簇命名 —— 三阶段复查的细化（Q5 核心）

用户决策：全自动优先，多轮逻辑复查，人工是备选。

### 为什么不直接用 c-TF-IDF 关键词当簇名
c-TF-IDF 产出的是"摇杆 / 漂移 / 说明书"这种关键词堆，不是人话。GTM 经理要的是"摇杆漂移精准度高"这种可直接写进文案的卖点表述。所以 LLM 命名必须上，但要解决它的不稳定性——这是三阶段复查的目的。

### 三阶段流程（细化）

```
簇内评价（N 条）+ c-TF-IDF 关键词
  │
  ├─ 阶段1 · 生成候选名
  │   输入：采样 5-8 条代表评价 + 关键词
  │   prompt：「这些手游外设用户评价共同称赞的卖点是什么？用一句 ≤12 字的人话概括，
  │            要具体（说'摇杆精准不漂移'，不说'手感好'）」
  │   输出：候选名 V1
  │
  ├─ 阶段2 · 交叉验证
  │   输入：V1 + 簇内另采样 5 条（与阶段1不重叠）
  │   prompt：「这些评价都在说『V1』吗？逐条答 是/否 + 一句理由」
  │   判定：≥4/5 答"是" → 通过；否则阶段1重生（最多 2 轮），仍不过 → 降置信度
  │
  └─ 阶段3 · 一致性收敛
      独立采样 2 次，各走一遍阶段1生成候选名 → 得到 V1'、V1''
      用嵌入余弦相似度比较 V1 / V1' / V1'' 的语义
      判定：三者两两相似度均值 ≥0.75 → 高置信；<0.75 → 低置信，标注 needsReview
```

### 置信度计算
`confidence = 0.6 × 阶段2通过率 + 0.4 × 阶段3收敛度`
- ≥0.8 高置信（直接用）
- 0.5-0.8 中置信（用，但标注）
- <0.5 低置信 → needsReview 进人工队列（**备选，不是必经**）

**诚实声明**：人工无法完全消除。三阶段能把人工介入压到"只处理低置信簇"，但"≥80% 簇名准确率"的验收标准本身需要人工抽样评估——这是评估，不是流程内人工。流程内人工只剩低置信簇复核。[需 spike 验证]：真实数据跑一轮，看低置信簇占比——若 >30%，说明命名 pipeline 要再调（可能是嵌入/聚类质量问题传导）。

## 决策 6：LLM 情感分类 —— 批处理与成本

- 复用 providers.ts（Ark/OpenAI/DeepSeek 可切）
- 批处理：评价逐条分类太贵，**打包批分类**——一次 prompt 喂 10-20 条，LLM 返回 JSON 数组（id → 正/负/中 + 置信度）
- 成本估算：单条评价 ~50 token，20 条一批 + prompt 开销 ≈ 1500 token/批。5000 条评价 = 250 批 ≈ 37.5 万 token——Ark coding plan 内可承受
- 准确性兜底：分类带置信度，低置信（如讽刺、混合情感）标"中"，不强行二分——宁缺毋滥，因为正向才进卖点榜

## Python 管道技术栈（具体包）

```
bertopic          # 主题建模框架（含 UMAP/HDBSCAN 依赖）
sentence-transformers  # BGE-M3 / MiniLM 加载
jieba             # 中文分词
pandas            # 数据清洗
openpyxl          # Excel 导出读取（电商评价）
```

**数据流**：
```
数据源(DataSource 接口, Node) → reviews.jsonl
  → Python 管道(voc_pipeline.py)：清洗→情感分类(调 LLM API)→嵌入→BERTopic 聚类→簇命名三阶段(调 LLM API)
  → clusters.json → Next.js 读取渲染榜单
```

**LLM 调用**：Python 管道直接调 provider HTTP API（复用 .env 的 key），不经 Node——减少一次进程间通信。

## 验证方案（spike 先行，关卡的硬要求）

铺开前必须先跑 spike（≤1 天）：
1. 准备 200-500 条小样评价（合成或公开渠道，手游外设品类）
2. 跑通 BERTopic + BGE-M3 + jieba 最小管道
3. 人工看 5 分钟：簇内评价是否真的在讲同一个卖点？（聚类质量的土办法验证，比任何指标都快）
4. 跑簇命名三阶段，看低置信簇占比
5. **决策点**：簇质量可接受 → 铺开；不可接受 → 先调嵌入/聚类参数，不进入 UI 开发

## 风险重估（比 spec §9 更细）

| 风险 | 新认知 | 缓解 |
|---|---|---|
| 中文聚类无直接基准 | 选型基于邻近证据，土办法人工看簇是最快验证 | spike 先行，不合格不铺开 |
| BGE-M3 体积大 | ~2GB，首次下载慢 | 一次性成本；备选 MiniLM 兜底 |
| 簇命名收敛度阈值 0.75 是拍的 | 无依据，需真实数据校准 | spike 时记录实际相似度分布，回调阈值 |
| jieba 分词对手游外设术语（"摇杆漂移""扳机键""宏定义"） | 通用词典可能切错 | 加载自定义词典（手游外设术语表），spike 时发现即补 |

## Delve 指引

- spike 跑出来之前，UI 不要开工——簇质量是地基，UI 是上层建筑
- 簇命名三阶段的 prompt 要在真实数据上调（特别是阶段1的"要具体"约束，手游外设的卖点表述方式）
- 若 BGE-M3 在 spike 中表现不佳，不要硬上——回 MiniLM 或 LLM embedding，中文嵌入模型的选择对簇质量影响是一票否决级
