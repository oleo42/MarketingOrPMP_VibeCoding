## 1. 问题定义

消费电子（手游外设）企业的用户反馈散落在电商评价、社媒内容等多个渠道。GTM 团队需要知道"用户真实喜欢我们产品的什么"（卖点共鸣），IPD 团队需要知道"用户集中抱怨什么"（产品问题）。当前靠人工翻评价，无法规模化、无法量化。

VoC 分析系统：多渠道用户反馈 → 情感分类 + 主题聚类 → **卖点共鸣榜**（本期交付）→ 反哺 GTM 内容策略；预留**产品问题榜**接口（后续扩展）。

## 3. 验收标准

1. **数据接入**：支持 ≥2 种数据源的接入接口（电商评价导出 + 至少一个抓取器），抓取器可插拔
2. **卖点共鸣榜**：输入一批评价，输出按声量排序的卖点主题榜，每个主题带：簇名、声量（条数）、代表性引文（3 条）、置信度
3. **簇名质量**：全自动命名 + 多轮复查，簇名准确率 ≥80%（抽样人工评估），低置信度簇自动标注
4. **可复现**：README 从零跑通（数据接入 → 聚类 → 出榜）
5. **面试可演示**：3 分钟 demo——导入评价 → 看卖点共鸣榜 → 点簇看引文

## 6. 系统架构

```
数据源层（可插拔）
  ├─ DataSource 接口：fetch() → Review[]
  ├─ 电商导出接入（Excel/CSV → Review）
  └─ 抓取器接入（社媒 → Review，本期至少 1 个实现）
       ↓
预处理层
  ├─ 清洗（去 HTML/广告/无意义短评）
  └─ 情感分类（LLM：正/负/中，带置信度）
       ↓
聚类层（本期核心）
  ├─ 嵌入（embedding）→ 向量
  ├─ 聚类（HDBSCAN 或 KMeans，簇数自适应）
  └─ 正向簇 → 卖点共鸣榜管道；负向簇 → 问题榜占位接口
       ↓
簇命名层（技术难点，Q5）
  ├─ 阶段1：LLM 生成候选簇名
  ├─ 阶段2：LLM 交叉验证（簇内样本 vs 候选名）
  └─ 阶段3：一致性校验（多次采样命名收敛度）→ 置信度
       ↓
输出层
  ├─ 卖点共鸣榜（簇名 + 声量 + 代表引文 + 置信度，按声量排序）
  └─ Web UI：榜单视图 + 点簇看引文
```

## 7. 关键技术决策

### 7.1 嵌入模型
- 候选：LLM provider 自带的 embedding 端点（Ark/OpenAI 都有）vs 本地 sentence-transformers
- **推荐**：本地 sentence-transformers（多语言，如 `paraphrase-multilingual-MiniLM-L12-v2`）——评价量大，本地嵌入零边际成本；LLM embedding 按 token 计费，大批量贵
- 风险：本地模型首次下载 ~500MB，但一次性

### 7.2 聚类算法
- **HDBSCAN**：簇数自适应、能识别噪声点（不相关的评价不归簇）——适合"不知道有多少个卖点"的场景
- 备选 KMeans：要预设簇数，不适合冷启动
- **选 HDBSCAN**，Python 有成熟实现（`hdbscan` 包）

### 7.3 簇命名三阶段（Q5 核心）

```
簇内评价（N 条）
  ↓ 阶段1：采样 5-8 条 → LLM "用一句话概括这些评价共同称赞的卖点"
  → 候选名 V1
  ↓ 阶段2：用 V1 + 簇内另采样 5 条 → LLM "这些评价都在说『V1』吗？回答是/否+理由"
  → 若多数否，重生候选名（最多 2 轮）
  ↓ 阶段3：独立采样 2 次，各生成候选名 → 比较语义相似度
  → 收敛（相似度高）→ 高置信度；发散 → 低置信度标注
```

**置信度计算**：阶段2 通过率和阶段3 收敛度的加权。低置信度簇进"待复核"队列（人工备选，不是必经）。

### 7.4 技术栈
- 复用母模板骨架：`template/src/{db,llm,lib,components}`
- 聚类是 Python 生态（hdbscan/sentence-transformers）——**决策**：聚类管道用 Python 脚本（独立步骤，输出 json），Node 端读结果渲染 UI。不在 Next.js 里硬塞 Python。
- 数据流：`数据源 → Python 聚类管道 → clusters.json → Next.js 读 json 渲染榜单`

### 7.5 数据契约

```typescript
// 统一评价结构（DataSource 接口的输出）
interface Review {
  id: string;
  source: string;        // 'jd' | 'tmall' | 'xiaohongshu' | ...
  product: string;       // 产品名/sku
  text: string;          // 评价正文
  rating?: number;       // 星级（电商有，社媒无）
  date?: string;
  url?: string;
}

// 卖点共鸣榜输出
interface SellingPointCluster {
  id: string;
  name: string;              // 簇名（三阶段命名产出）
  confidence: number;        // 0-1，命名置信度
  reviewCount: number;       // 声量
  exemplars: string[];       // 代表性引文 3 条
  needsReview: boolean;      // 低置信度 → 进人工复核队列
}
```

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 抓取被封/反爬 | 抓取器独立可插拔，被封只影响该源；电商导出作为保底数据源。README 红线 3：优先导出数据，抓取注意 ToS |
| 簇名质量不达标 | 三阶段复查是主防线；低置信度自动标注进人工队列（备选）；抽样人工评估 ≥80% 才验收 |
| 嵌入模型中文效果差 | 用多语言模型（paraphrase-multilingual）；若簇内评价混乱，降级用 LLM embedding（成本高但准） |
| 无真实语料冷启动 | 先用合成/公开小样跑通管道；真实数据用户后续补充，聚类参数随真实数据调 |
